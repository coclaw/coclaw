Fix the "double-bubble" rendering bug where one agent reply could appear in the chat as two separate bot bubbles — the upper one stuck on "thinking…" forever while the lower one shows the same final text with a model name and timestamp. The root cause is that `loadMessages.doLoad` chains `sessions.get` (which sets `this.messages`) → `__reconcileRunAfterLoad` → `chat.history` (which sets `currentSessionId`) inside one shared try block, and propagates any failure of the second RPC as the whole function returning `false`. When this happens inside `__awaitPersistAndDrop` after a run terminates (most observably when a DC abnormality leaves `chat.history` either rejecting or hanging until its 60s timeout), the upstream `if (ok) runsStore.dropRun(...)` is skipped, so the run's `streamingMsgs` are never released. `allMessages` then merges the still-live optimistic user/claw entries with the already-persisted server messages, and `groupSessionMessages` splits them into two `botTask` items because the residual optimistic user separates the streaming assistant from the persisted assistant. The fix decouples `dropRun` from the auxiliary `chat.history` RPC by adding an `onMessagesPersisted` hook to `loadMessages` — the hook fires synchronously the moment `sessions.get` has succeeded and `this.messages` is committed, and `__awaitPersistAndDrop` uses it to invoke `dropRun` immediately rather than waiting for the rest of the function. To keep the same promptness when an unrelated silent reload is already in flight, the in-flight guard now also routes a late-arriving hook to either fire immediately (if the in-flight load has already committed `this.messages`) or queue and drain when it does. `chat.history` is additionally wrapped in its own non-fatal try/catch so its failure preserves the previous `currentSessionId` and never affects the boolean return value. With this layout, `dropRun` runs at the moment the persisted server data is in place, eliminating the double-bubble visibility window. Verified by a server-log trace where one `agent.run.end reason=failed` had no matching `agent.run.drop` for ~17 minutes until a fresh `register` superseded the runKey.
